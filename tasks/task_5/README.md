# Задача 5. Мультитенантная партнёрская платформа

## Модель изоляции

Партнёр — это **tenant**, то есть изолированный контур одной организации. Для каждого партнёра создаются отдельные PostgreSQL-БД доменов, ключ шифрования в **KMS** (сервисе управления ключами), набор топиков и consumer group Kafka, правила доступа к Kafka (**Kafka ACL**) и отдельная папка в объектном хранилище. Kafka ACL определяют, какие приложения партнёра могут читать или записывать конкретные темы Kafka. Поэтому данные, резервные копии и права доступа одного партнёра не затрагивают других.

Пассажир и водитель работают через мобильные приложения GoFuture. Это общий клиент с настройками и брендированием конкретного tenant, а не отдельное развёртывание приложения для каждого партнёра. Оператор и администратор партнёра работают только через веб-портал партнёра.

Kafka не выдаёт права самостоятельно. Keycloak создаёт техническую учётную запись сервиса и выдаёт ей учётные данные. Сервис подключается к Kafka через SASL/OAuth или mTLS, а брокер Kafka проверяет эту учётную запись по ACL при каждом чтении или записи темы либо consumer group. Например, `booking-tenant-a` может писать в `tenant-a.booking-events` и использовать группу `tenant-a.booking`, но не имеет доступа к ресурсам `tenant-b.*`. При подключении партнёра автоматический настройщик создаёт эти ресурсы и ACL только для его сервисов.

Доменные сервисы работают в общем контуре приложения и не хранят состояние конкретного партнёра в памяти. API Gateway проверяет токен пользователя, определяет tenant по проверенному источнику токена и области учётных записей партнёра, затем передаёт этот контекст сервисам. Реестр партнёров возвращает конфигурацию, подключение к БД и включённые функции. `tenant_id` из тела или параметров запроса не считается доверенным. Сервис использует только подключение, выданное реестром для проверенного tenant. Для Kafka он выбирает учётную запись и топики этого tenant; поле `tenant_id` внутри события не участвует в проверке доступа брокером.

Кастомизация не создаёт отдельную ветку кода: конфигурация партнёра и флаги функций определяют доступные модули, правила, интеграции и брендирование. Изменение флага аудитируется и применяется в границах одного tenant.

## IAM и SSO

**IAM** — управление пользователями и их правами. **SSO** — единый вход: оператор или администратор партнёра может войти через корпоративную учётную запись. Для этого используется **Keycloak**: отдельный realm (изолированная область учётных записей) для сотрудников GoFuture и отдельный realm для каждого партнёра. Realm партнёра подключается к его корпоративной системе входа по OIDC или SAML. Gateway проверяет подпись, источник, получателя, срок токена и роли; сервисы дополнительно проверяют разрешённые операции.

| Роль | Граница данных | Доступ |
|---|---|---|
| Администратор платформы | Все tenant, без бизнес-данных по умолчанию | Создаёт и блокирует tenant, управляет шаблонами ролей, SSO и настройками подключения; бизнес-данные доступны только по отдельной аварийной процедуре. |
| Инженер сопровождения (SRE) | Все tenant, только технические сведения | Просматривает агрегированные метрики, логи без ПДн и аудит; не изменяет заказы, платежи или настройки партнёра. |
| Администратор партнёра | Только свой tenant | Управляет пользователями, ролями, SSO-настройкой, флагами функций и техническими учётными записями своего партнёра. |
| Диспетчер | Только свой tenant | Читает и изменяет заказы, поездки и назначения водителей в рамках назначенных прав. |
| Бухгалтер | Только свой tenant | Читает платежи, выплаты и финансовые отчёты; не создаёт поездки и не управляет IAM. |
| Аналитик | Только свой tenant | Читает агрегированные витрины ClickHouse и DataLens; не получает доступ к рабочим БД и платёжным данным. |
| Техническая учётная запись интеграции | Только свой tenant | Вызывает партнёрский API в явно выданных разрешениях; не имеет интерактивного входа и прав администратора. |

## Автоматическое подключение партнёра

1. Администратор платформы создаёт заявку в портале партнёров: регион, SSO-параметры, модули, интеграции и брендирование.
2. Сервис подключения добавляет партнёра в реестр со статусом «подготавливается» (`PROVISIONING`). Пока этот статус не изменится, клиентский трафик не принимается.
3. Сервис создаёт realm и роли Keycloak, подключает корпоративный вход, создаёт технические учётные записи; затем создаёт БД, KMS-ключ, применяет миграции, создаёт папку в объектном хранилище, а также топики, consumer group и ACL Kafka.
4. Сервис проверяет вход через SSO, доступ к БД и право технической учётной записи работать с ресурсами Kafka этого tenant.
5. При успехе сервис переводит партнёра в состояние «активен» (`ACTIVE`) и направляет администратору инструкцию SSO. При ошибке статус становится «ошибка подключения» (`FAILED`), доступ не выдаётся, а повторный запуск создаёт только недостающие ресурсы.

## Наблюдаемость

Prometheus, Grafana, Loki и Alertmanager собирают доступность сервисов, ошибки авторизации, задержки запросов, здоровье БД и правил доступа Kafka, статус подключения и изменения флагов функций. Метки содержат ограниченный `tenant_id`, сервис и регион, но никогда не содержат пользователя, заказ или платёжный идентификатор. Логи и трассировки включают tenant-контекст только для поиска и не содержат ПДн или секретов.

Администратор tenant получает алерты о собственных SSO и интеграциях; SRE получает алерты инфраструктуры и массовых ошибок. Неизменяемый аудит фиксирует вход, изменение ролей, выдачу технической учётной записи, доступ к секретам, изменение конфигурации и все переходы подключения.
