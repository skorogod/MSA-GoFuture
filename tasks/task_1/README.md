# Задача 1. Переход GoFuture от монолита к микросервисам

Задача описывает целевую архитектуру GoFuture и безопасный поэтапный переход от Django-монолита. Проектный вариант сохраняет работу существующего продукта во время миграции: новая функция постепенно заменяет legacy-функцию, после проверки трафик переключается, а при проблеме возвращается на прежний маршрут.

**Статус:** решения являются проектными и находятся на рассмотрении.

## Основные решения

- Декомпозиция выполняется по паттерну Strangler Fig: Booking, Driver, Pricing, Payments, Payouts, Notification, Geography, Fraud и Analytics становятся отдельными доменными сервисами.
- Каждый сервис владеет своими данными. На переходный период обращения к ещё не выделенным функциям монолита проходят через ACL — слой, который переводит новый контракт в legacy-контракт.
- Gateway по флагу маршрута направляет запрос либо в новый сервис, либо в монолит. Один запрос не должен одновременно обрабатываться обеими реализациями.
- Сервис-издатель записывает бизнес-изменение и строку transactional outbox в одной транзакции PostgreSQL. Debezium Outbox Event Router читает запись из WAL и публикует событие в Kafka.
- Kafka предназначена для доменных и аналитических событий. RabbitMQ сохраняется для существующих Celery-задач на переходный период; перенос или окончательное сохранение каждой задачи принимается отдельно.
- Приоритетный кандидат на первое выделение — Booking. Для каждого домена определены собственные данные, порядок миграции, проверка и условия отката.
