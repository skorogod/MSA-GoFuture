# Задача 2. Событийная архитектура заказа и оплаты поездки

В задаче описана целевая событийная архитектура процесса заказа поездки GoFuture — от создания бронирования до окончательной оплаты после завершения поездки. Подготовлены архитектурные решения и C4-диаграмма уровня C2 с инструментами мониторинга.

**Статус:** архитектурные решения находятся на рассмотрении. Диаграмма и ADR описывают предлагаемый вариант, а не уже развёрнутую систему; детали реализации необходимо согласовать и проверить на пилоте.

Эта схема ограничена процессом заказа и оплаты. Полный состав доменных сервисов, их хранилища и общая событийная платформа показаны в [целевой C2-диаграмме задачи 1](../task_1/diagrams/C2_to_be.puml).

## Основные решения

- Для координации процесса предложена **Parallel Saga** с асинхронным обменом и итоговой согласованностью. Независимые шаги могут выполняться параллельно, если это допускают бизнес-правила и доступны необходимые данные.
- Для отдельного от Booking оркестратора предварительно выбрана **Camunda 8 Self-Managed**. BPMN-процесс управляет шагами, ожиданиями, повторами и компенсациями; бизнес-операции выполняют сервисы-владельцы данных.
- **Apache Kafka** предлагается для команд и событий. Kafka-адаптер связывает Camunda с брокером, а Python-сервисы используют потребителей на `confluent-kafka-python`. Способ интеграции адаптера и обработку сбоев ещё нужно спроектировать и проверить.
- Сервис-участник сохраняет локальный результат и исходящее событие в **transactional outbox** одной транзакцией PostgreSQL; Debezium Outbox Event Router публикует запись в Kafka. Это не делает состояние Camunda и Kafka атомарными — восстановление адаптера проектируется отдельно.
- Kafka key содержит **UUID региона владения заказом**. Описаны структура сообщений, правила повторов и DLQ для групп потребителей; порядок между разными топиками не гарантируется.
- На переходный период функции, остающиеся в монолите, доступны через **ACL**, а существующие задачи Celery могут продолжать использовать **RabbitMQ**.
- Для наблюдаемости предложены **Prometheus / TSDB и Alertmanager** для метрик и алертов, **Grafana Alloy и Loki с Yandex Object Storage** для логов, **OpenTelemetry и Jaeger с отдельным Elasticsearch** для трассировок. Grafana используется для просмотра данных.

## Процесс саги

1. Booking создаёт заказ и записывает событие запуска саги в transactional outbox; Debezium публикует его в Kafka.
2. Geography проверяет зону; затем выполняются необходимые расчёт стоимости, проверка Fraud и поиск водителя. Допустимые независимые шаги могут выполняться параллельно.
3. Driver назначает водителя, а Booking подтверждает заказ после успешного завершения обязательных шагов.
4. Оркестратор сохраняет состояние ожидания завершения поездки. После её завершения Pricing рассчитывает итоговую стоимость, а Payments проводит оплату; результат фиксируется в Booking.
5. При ошибке до подтверждения заказа выполняются необходимые компенсации, например освобождение водителя и отмена бронирования. При неизвестном результате оплаты Payments сверяется с провайдером, не повторяя списание вслепую.

Окончательная оплата входит в сагу. Предварительная блокировка средств при заказе остаётся открытым вопросом; выплаты водителю и возвраты после завершённой оплаты рассматриваются отдельно.
